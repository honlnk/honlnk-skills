# linkseek 搜索工具使用指南

linkseek 是自托管的 SearXNG 元搜索 + 网页抓取服务。本技能解决五个问题：工具怎么选、查询怎么写、失败了怎么办、**异步任务怎么用**（第五节）、以及**怎么让这套用法越用越准**（第八节）。前四件事做错任何一件，都会显著提高空结果率或浪费轮次。

## 一、工具怎么选

| 需求 | 工具 | 耗时 |
|---|---|---|
| 只要结果列表（标题/URL/摘要） | `web_search` | ~2s |
| 要多个页面的正文自己读 | `web_search_and_fetch` | 视抓取数 |
| 要一个问题的直接综合答案 | `web_search_answer` | ~10-30s |
| 抓单个已知 URL | `web_fetch` | ~1s，稳定性极佳 |
| 单 URL 抓不到（SPA/WAF/403） | `web_fetch_render` | ~40s，兜底用 |
| 对单个页面内容提问 | `web_fetch_answer` | ~11s |
| 查后台配置了哪些 AI 模型（供 `model` 参数选择） | `list_models` | ~1s |
| 中等复杂度的深度调研（可脱手） | `web_research`（纯异步） | 1-3 分钟，提交即返回 |
| 查异步任务进度 / 取结果 | `get_result` | ~1s |

选择原则（三分法定位）：

- **简单**（查一个事实/一个页面）：同步工具直接用——`web_search` / `web_fetch` / `web_search_answer` / `web_fetch_answer`，更快更省事
- **中等**（一个问题需要多轮搜索、多来源交叉，但你不需要盯着过程）：`web_research` 脱手（第五节），或对四个慢工具传 `defer=true`
- **复杂/开放**（需要你边搜边决策方向、迭代查询策略）：自己多轮 `web_search` / `web_search_and_fetch`，流程控制在 Agent 手里
- 不确定就先 `web_search`（轻、快），摘要够就直接用，不够再抓正文
- **URL 已知时永远直接 fetch，不要去搜索**

## 二、查询怎么写（最容易踩的坑）

写成搜索引擎友好的关键词，**不要写完整句子**，**不要用搜索运算符**：

✅ 好的写法：
- `Next.js 15 app router 迁移`
- `微信 扫码登录 个人开发者`
- `GLM-5 context window size`

❌ 会导致空结果的写法：
- 完整句子：`如何用微信扫码登录而不用企业认证` —— 召回差
- 运算符：`"Agent工程师" OR "智能体工程师" 招聘` —— 部分引擎不支持 OR/引号，直接 0 结果
- `site:github.com webfetch mcp` —— site: 同样不被所有引擎支持；想限定域名用 `preferred_sites` 参数

中文查询直接写中文，**不需要也不应该传 `language` 参数**（见下节）。

`web_research` 的 `question` 例外：可以传自然语言问题（服务端会先做独立问题改写再生成关键词查询），但同样不要带运算符。

## 三、参数手册

| 参数 | 用法 |
|---|---|
| `language` | **默认不传。** 实测显式传 zh-CN 会把空结果率从 ~8% 拉到 ~32%（部分引擎收窄召回）。SearXNG 按查询内容自动处理语言。 |
| `categories` | 技术问题传 `it`；学术论文 `science`；新闻 `news`。不确定就不传。 |
| `preferred_sites` | 想优先某些站点时传域名数组，如 `["github.com", "docs.anthropic.com"]`。比 site: 运算符可靠。 |
| `timeRange` | 要最新内容传 `month` 或 `day`（没有 week）。 |
| `engines` | 一般不传。仅当空结果诊断信息建议时按建议传（如 `bing,google`）。 |
| `maxResults` / `fetchCount` | 默认 10 / 3 够用；调研类任务可放宽到 15-20 / 5。 |
| `defer` | 四个慢工具（`web_search_and_fetch` / `web_search_answer` / `web_fetch_answer` / `web_fetch_render`）可用：传 `true` 立即返回 taskId，不阻塞等待。用法见第五节。 |

## 四、搜索失败时怎么办（读懂诊断）

服务端已内置自动降级重试（原参数 → 去 language → 去 categories → 换 bing,google 引擎），所以**你拿到的空结果已经是服务端尽力后的结果**。空结果返回格式：

```
未找到与「xxx」相关的结果。
已自动尝试 3 组参数：原参数(0 条) → 去掉 language(0 条) → engines=bing,google(0 条)。
无响应引擎：google、bing（可能被上游限流或网络故障）。
建议：把查询改写为更简洁的关键词（去掉引号 / OR / AND / site: 等搜索运算符）后重试一次；若仍无结果，可能是引擎侧故障，建议改用其他搜索途径并稍后再试。
```

标准应对动作（按序执行，不跳步）：

1. **改写查询重试一次**：砍成更短的关键词、去掉所有运算符。只重试这一次，不要反复改写轰炸。
2. 改写后仍空，或诊断显示「无响应引擎」覆盖了主要引擎 → **判定引擎侧故障**：换内置 WebSearch 完成当前任务，并告知用户 linkseek 搜索引擎侧暂时故障。
3. **绝不要**：原样重发同一查询、连续换 engines 碰运气、或把空结果当成「网上没有这个信息」写进结论。

（旧版服务返回的空结果不带诊断（只有一句"未找到…建议：或用 engines 显式指定引擎"），应对流程相同：改写一次 → 仍空则换内置搜索。）

## 五、异步任务用法（defer 脱手 / web_research）

**什么时候用**：调用发起后你还有别的事可做（可以并行推进任务的其他部分），或任务本身耗时长（`web_fetch_render` 抓慢站点、`web_research` 全程 1-3 分钟）。如果下一秒就要用结果且无事可做，同步调用更简单——不要为了异步而异步。

**标准流程**：

1. 提交：慢工具传 `defer=true`（或直接调 `web_research`），立即拿到 `taskId`
2. 等待：先干别的活；没有别的活就 sleep 15-30 秒
3. 取结果：`get_result(taskId)` —— 未完成会返回当前进度（含轮次/抓取数文案），**不要无间隔连刷**；完成了返回的内容与同步调用格式完全一致
4. 过期与丢失：完成结果保留 60 分钟；服务重启后任务丢失（返回「不存在」），此时重新提交即可

**web_research 档位选择**：

| depth | 轮数/来源 | 适用 |
|---|---|---|
| `fast` | 1 轮 / 3 来源 / 不蒸馏 | 快查验证，~20-40s |
| `standard`（默认） | 3 轮 / 5 来源 / 蒸馏 | 常规调研 |
| `deep` | 5 轮 / 8 来源 / 蒸馏 | 全面综述，最慢 |

**纪律**：同时挂起的异步任务别太多（服务端有并发上限，超了会排队）；提交后忘了取结果是纯浪费——安排好取结果的时机再提交。

## 六、与内置 WebSearch 的关系

- **默认优先 linkseek**：自托管、参数可控、抓取链路强（`web_fetch` 实测稳定，内置 WebFetch 对部分技术站会 404）。
- 内置 WebSearch 走商业搜索 API，召回更稳但不支持任何参数、仅美区视角。定位是 linkseek **引擎故障时的兜底**，或按第四节流程走完后的第二选择。
- 不要同轮并行对冲（同时调 linkseek + WebSearch）：浪费轮次和配额，先走完第四节的流程再切换。

## 七、已知边界

- 图片/视频检索：`categories=images|videos`，摘要质量一般，重要任务建议用专门的视觉工具直接分析图片
- 抓取遇 403/429/空正文：换 `web_fetch_render`（Playwright 渲染）
- 搜索结果偶有低质页面混入（威客站/登录页）：引用前扫一眼 URL 域名是否与查询主题切题
- 异步任务为内存态：服务重启即丢（`get_result` 会明确告知「不存在」），完成结果 60 分钟过期
- 本技能对应的空结果诊断格式依赖 linkseek 2026-09-28 之后部署的版本；异步任务系统依赖 2026-09-29 之后部署的版本（`defer` / `web_research` / `get_result` 不存在说明服务端未更新）
- 本技能创建于 2026-09-28，用法尚未经过大量真实使用验证，存在过时或错误的可能——这正是第八节存在的原因

## 八、自主实验与技能进化

本技能的写法不是圣旨，是当前最优假设。**允许且鼓励 Agent 在真实任务中尝试新方法**，验证有效后沉淀回来，让技能越用越准。对每个部署者来说，自己的真实场景就是测试场。

### 8.1 什么时候做实验

- **标准流程失败后**：第四节流程走完仍空结果、准备换内置搜索之前——这是零额外成本的实验窗口（反正要再搜一次）
- **结果质量异常时**：拿到结果但明显跑偏（垃圾域名占主体），怀疑有更好的参数组合
- 不必主动空跑实验：正常拿结果的搜索就按本技能执行，不要为了实验而实验

### 8.2 实验规则（控制成本与噪声）

- 每个失败场景最多尝试 **2 个新变体**，试完仍无效就按第四节判故障/换内置搜索
- 可变的维度：`engines` 组合（如 `bing`、`wikipedia`、`ddg`）、`categories`、`timeRange`、查询改写风格（中英对照词、加年份、删停用词、拆成更短的词组）
- **内置 WebSearch 可当对照组**：新方法仍空时用内置搜一次——内置有结果而 linkseek 空 → 是引擎侧问题（也值得记录）；两边都空 → 信息可能真不存在
- 判定标准：同一意图下，新方法拿到相关结果而标准方法为空，或结果切题率明显更高

### 8.3 记录发现

把实验结果按模板追加到本技能目录的 [`references/findings.md`](references/findings.md)（不必加载进上下文，写文件即可）。状态分三级：

- **候选**：单次验证有效
- **已确认**：不同会话/不同查询复现过 ≥2 次 → 此时应向用户上报
- **已失效**：旧结论在新环境不再成立（引擎行为会漂移，超过约 3 个月未复现的方法降级或删除）

### 8.4 上报与进化（重要：动文件前必须经用户同意）

发现「已确认」级的方法时，在当次回答里顺带向用户讲清楚三件事：

1. 标准方法当时的结果（空 / 跑偏）
2. 新方法及其结果（附来源）
3. 建议怎么改：并进第几节、改成什么表述

**经用户明确同意后**才编辑本 SKILL.md 正文（把方法并进对应章节，保持各节简洁，发现细节留在 findings.md）；用户不同意就只留在 findings.md 里继续积累。**任何时候都不得未经同意改动本文件。**
