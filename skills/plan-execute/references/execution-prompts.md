# 施工提示词模板

交给独立施工会话（或 goal 指令）使用的提示词结构。核心要求：**自包含**——施工会话没有本项目的历史上下文，一切事实来源是提示词 + 计划文档。模糊处会被省事路径填补，所以宁可写细。

## 施工提示词结构

### 1. 总纲

- 任务一句话：本次做什么、依据哪几份计划文档（给**完整路径**，并要求开工前重读全文——摘要二手转述会丢约束）。
- 仓库 / 分支 / 工作目录。
- 门禁基线：当前测试数、测试命令、类型检查命令。
- 提交规范：让施工方**先读仓库的 commitlint / 贡献规范确认合法的前缀与 scope**，再提交（凭惯例写会被打回返工——两个真实会话都踩过）。
- 硬约束：不 push；文档随手同步（索引流转 + 施工日志）；发现计划外问题记入日志、不随手改。

### 2. 分阶段任务清单

每个阶段 / 波次写清：

- 对应计划文档的哪几节（阶段开工前重读那几节）；
- 施工点精确到文件，必要时报行号；
- 每个行为改动要求补的测试（**时序 / 竞态类必须是事件序测试**——模拟乱序事件序列做断言）；
- 阶段门禁：测试全绿 + 类型检查干净 + 本阶段手动验收场景（写具体场景，不写「确认没问题」）。

### 3. 偏差与交付要求（整段照抄进提示词）

> - 允许你在发现计划方案有破绽时改方案，但必须在提交信息里写明推翻理由：原方案为什么不行、新方案好在哪。沉默地改方案等于埋雷。
> - 一切「任选其一 / 暂缓 / 简化」当场记入施工日志，并在最终汇报中逐条讲明：做了什么取舍、为什么、对用户意味着什么。
> - 无法完整验证的验收项（缺 API key、原生对话框无法自动化等）：降级验证 + 明示需要用户真人复核什么。
> - 最终汇报必须包含三节（没有就写「无」）：**未按计划实现**（含原因）、**未验证清单**、**留下的尾巴**（含用户影响）。

## 修复批提示词模板

结构同上，任务清单换成逐条修复项，每条给：

- 现象（用户可感知的症状，不只技术描述）；
- 机理（为什么会这样，精确到 `文件:行号`）；
- 修法方向（写方向和约束，**注明「发现修法有破绽时允许改方案，理由写进提交信息」**——提示词里的方案也可能是错的，真实案例：建议用「缓存存在性」判断删除态，施工方发现缓存淘汰会误伤，改用墓碑集合，是更好的方案）；
- 要求补的测试（时序类：事件序测试）。

## 反面教训（这些条款为什么存在）

| 教训 | 条款 |
| --- | --- |
| 「任选其一」导致高频控件被埋进设置页深处，用户自己发现 | 计划中用户体验取舍拍死；提示词不留开放选择题 |
| 默认值变更不写迁移条款，旧配置继续生效，升级收益为零 | 总纲固定检查项：「本改动有无旧数据 / 旧配置要迁移？」 |
| 时序 bug 无事件序测试，修复后 review 才发现竞态 | 每条修复项要求补事件序测试 |
| commit 前缀凭惯例写，被 commitlint scope-enum 打回返工 | 总纲要求先读仓库提交规范 |
| 验收环境知识每轮重新摸索（mock 端口、原生对话框限制等） | 查到的环境知识记入项目文档，提示词直接引用 |
